# Design Report

## 1. Architecture

The code currently follows a synchronous process to prioritize simpler debugging, easier traceability, immediate feedback, and transactional safety. The synchronous process ensures the checkpoints are straightforward and easy to reason about. They also better regulate the strict, sequential requirements of this project, which is important to consider for the sensitive data banks might own. The immediate feedback is also useful for applying the agent to other websites. As stated in the assignment description, other DOMs might be less stable or predictable than expected, and though a queue might be able to move onto other work, the organization and traceability of the error-handling might save time in the long-term.

The architecture of the Workflow Agent considers flexibility and safety in its design. Its main boundaries are workflow discovery, surface interaction, policy enforcement, persistence, and replay. `DiscoveryAgent` is the LLM-driven component: it requests one JSON action at a time and supplies the goal, current observation, and completed step history. `SurfaceAdapter` uses Selenium WebDriver to navigate, inspect visible page text, locate controls, enter values, select options, and verify information. `SafetyPolicy` validates actions, URLs, administrator targets, sensitive inputs, and human-approval gates. `RunRecorder` writes JSONL event logs and a JSON workflow artifact; `ReplayEngine` consumes the recorded ordered steps and typed invocation values; and `ChatBot` supplies goal entry, operator prompts, and the live control panel. The boundaries are modules in one process, not separately deployed services. This keeps the prototype straightforward to run and debug.

The browser surface is kept behind a small adapter rather than exposing Selenium calls throughout the agents. This makes replay testable with fake surfaces and keeps browser-specific selection behavior in one place. Discovery is intentionally more flexible than replay: a model can help construct a workflow, but replay executes only what's acceptable in the .json file. The trade-off is that discovery can vary between runs while an accepted artifact is much more repeatable.

## 2. Artifact schema

The artifact stores a variety of information, including the version, artifact type, workflow id, parameters, and steps. The workflow id serves as a keyword indicator for the operator's "goal input" from the chatbot. After identifying the workflow, the Goalparser verifies that the required variables exist for that workflow id; it uses extra variable identifiers and distance calculations from the keyword to choose the closest option. This allows flexibility in the operator's phrasing. The steps include an "action" that the agent must extract, validate, and perform during the runtime. Most actions include a strategy (such as a function that the code should execute), a value (such as the amount or account number), a purpose, and a robustness indicator.

Purpose and robustness indicator have no impact on the code; they exist for readability. Action values serve as placeholders like `{{amount}}` so actual invocation data is supplied at replay time instead of being embedded in the workflow. This decision allows the inputs to vary and maintains confidentality with financial data. Outputs are named declarations with an extraction strategy and scalar type. `output_schema` describes the exact object returned by replay, including its property types and required fields. A `success_check` is the completion checkpoint; optional `business_outcomes` hold exact text matches that represent legitimate results such as a missing member.

Validation enforces the required version `1.1` fields before persistence and checks that parameter references and output shapes agree. The schema is deliberately limited to scalar input/output values and a text checkpoint; nested output objects and arbitrary checkpoint strategies are not implemented.

## 3. Determinism & error handling

Replay follows the artifact's step list in order, validates each step against the safety policy, resolves only declared parameters, and checks the checkpoint before returning success. Surface targeting tries explicit selectors first and uses the semantic purpose as a fallback. The success result includes extracted, type-coerced outputs so that an artifact cannot be reported successful merely because its actions ran.

After each action, replay inspects the visible page state. Declared business outcomes take priority, followed by built-in “not found” patterns. These ditinguish `business_outcome,` such as "account not found" from application crashes. Validation messages, permission denials, session expiry, load errors, and other exceptional states return `failure` with a stable code/category, step number, action, expected condition, observed URL/title/text excerpt, and error details. Unexpected browser dialogs are not automatically accepted or dismissed, for replay stops and reports their text where available.

Navigation and element-wait operations may retry once after a page-readiness check. Clicks and other potentially side-effecting actions are not blindly retried. The retry limit and structured recovery event make this behavior bounded and auditable. UI drift is secondary to runtime failure. This is because CSS-to-semantic fallback can absorb modest markup changes, whereas unresolved targets stop the run.

Each run writes action/recovery/result events to JSONL. Terminal failures also capture a screenshot when the browser and recorder are available. This improves diagnosis without a full DOM dump. Model-generated discovery remains nondeterministic; determinism applies to replay of a given artifact and inputs, which is subject to the external application state.

## 4. Heterogeneity & multi-tenant

The project is implemented in Python 3.9+ because of its mature browser automation, sensible AI ecosystem, convenient JSON handling, and fast iteration. Although this project has attempted to tackle the heterogeneity of other websites, it recognizes that adjustments might also be necessary for future implementation. Python creates a future foundation for developers to add additional surface adapters or surface boundaries for wider website applicability. The nature of the language-such as library imports-allow the developer to quickly adjust the prototype for these alterations, which save programming time when bugs arise.

The seam is between the recorded flow and the code that perceives/acts on a particular surface. The artifact describes the logical operations and intent; it also includes a locator profile with surface-specific alternatives when the primary intentional fails. The robustness rationale describes these intentions for the sake of readability. If future developers handle this project, the intent is to provide them with enough context so that they can address the heterogeneity limitations without having to spend too much time in the code. The replay engine owns ordering, parameter binding, policy gates, retries, outcome classification, checkpoints, and result construction. Meanwhile, the surface adapter owns observation and translates each logical target/action into the UI's native operations. The current `SurfaceAdapter` is Selenium/web-specific; it is not yet the proposed cross-surface interface, which can be expanded upon in the next iteration.

For a legacy web app, a new adapter could use CSS/XPath, accessible labels, frame-aware lookup, and page-specific readiness checks while implementing the same logical action contract. Locator alternatives should be ordered and scoped (for example, stable element ID, accessible name, then a constrained CSS fallback) with ambiguity treated as an error. For a desktop app, a separate adapter would use accessibility/UI Automation identifiers and window/dialog state. Browser selectors must not be carried over as desktop locators. Artifacts can share the logical step and output contract, while naming a compatible adapter/locator profile, for adapter-specific data remains isolated from the workflow's business intent.

For hundreds of tenants and roughly twenty apps each, I would avoid storing a full independent recording for every tenant. I would separate the artifact into four versioned layers: (1) a vendor-product workflow template keyed by vendor, product, workflow, and supported app version; (2) an application/surface binding with selectors, readiness rules, checkpoints, and output extraction; (3) a tenant binding containing only approved differences such as base URL, locale, feature flags, and policy profile; and (4) per-invocation typed inputs. Resolution would be deterministic and auditable: pinned template version, then compatible app binding, then an explicit tenant override, then invocation data. An override would patch named fields rather than copy the whole artifact, declare its parent version and rationale, and be validated against the same schema and safety policy. Secrets and tenant data would live in a separate secret/session store, never in a shared artifact or source repository.

Drift should be detected, not silently learned into a shared template. Each app binding would declare supported product/build versions and optional fingerprints for key pages or controls. At run start, the adapter would check app identity/version and required anchors; during replay it would report locator fallback use, missing/ambiguous targets, changed checkpoints, and output mismatches. A mismatch would quarantine or mark that app/tenant binding as needing review while preserving the last know, validated version. Drift reports can be grouped by vendor version and tenant to distinguish a common vendor change from a tenant-specific customization. A reviewed fix is tested against a representative fixture and affected tenant profiles, versioned as a new binding, and rolled out gradually with rollback. The current project does not implement this registry, layering, fingerprinting, or rollout system: its `SafetyPolicy` is hard-coded for ParaBank and it has no tenant isolation or shared-session management. As specified earlier, these are design extensions, not existing proudction capabilities.

## 5. Escalation & handoff

When replay reaches an actionable blocked state, it records the current goal, step, page state, and reason; captures screenshot evidence; and presents a chatbot human-review request. The runtime control panel also lets an operator take control between action boundaries and return control to automation. If the operator acknowledges a failed step, the result is still considered a `failure`; a later replay must verify the checkpoint before claiming success.

Dead browser sessions and blocking unexpected dialogs skip chatbot injection because the browser may not accept scripts. They return structured failures instead. If no chatbot is available, replay can still return the failure and evidence. A production deployment should add an external notification channel and explicit operator identity/audit data.

## 6. Safety

The safety layer restricts navigation to HTTPS and the configured host, blocks administrator targets, disallows credential inputs, and requires human approval before transfer submission. Sensitive invocation fields are prompted without echo in the demo CLIs; artifacts contain parameter declarations and placeholders rather than entered values. Logs redact common account, amount, and credential patterns, and generated reports are ignored by Git. Before a failure screenshot is saved, the recorder temporarily masks editable controls and likely financial text/fields identified by labels, attributes, and common account/currency patterns, then restores the page.

These are application guardrails, not a security boundary. Locator purpose text and language-model proposals can be ambiguous; phrase-based redaction, page-text classification, and screenshot masking can miss new formats or unlabelled static content. A screenshot may therefore still contain sensitive data, and a host allowlist does not establish that a page is trustworthy. Operators must review high-impact actions, protect local report files, and keep API keys outside the repository.

Outside of the current project, another safety consideration was the LLM model, `gpt-4.1-mini.` Although cost-effective and efficient, this mdoel scored high in following strict protocols and answering questions without losing details, adding to the safety component of the assignment.

## 7. Cuts

This version deliberately leaves out production authentication and secret storage, CAPTCHA/2FA automation, a complete offline website/model simulator. It also excludes long-running retry/backoff policies, full DOM/trace capture, nested output schemas, and non-Windows browser selection. It does not provide a generalized tenant configuration or desktop automation adapter. The next steps would be to make error/outcome declarations fully configurable per workflow, add integration tests against a controlled local web fixture, improve schema migration tooling, and introduce isolated tenant-specific adapters and policies before broad reuse.
